# Release NF0T-Logger

Publishing is done by CI, not by you. Your job is to get a correct version bump and a correct
release PR onto `main`; `release.yml` does the rest. Every merge in this procedure waits for
the user's explicit go-ahead.

## Hard rules

- **Never** run `git tag`, `gh release create`, or `gh release edit --draft=false`, and never
  publish a draft release in the web UI. GitHub Immutable Releases locks a release and **burns
  its tag name forever** the moment it is published; an asset-less publish cannot be repaired.
  This is how `v26.9.1` was lost.
- Never push directly to `develop` or `main` (both are protected). Everything goes through a PR.
- Feature/bump PRs into `develop`: **squash**. The release PR `develop` → `main`: **merge commit**
  (`--merge`), so each commit's `Fixes #N` closes its issue on the default branch.
- Do not merge any PR without the user saying so.

## 1. Compute the version

Format: `YY.MM.W`. `W` is the week of the month, where weeks are **Sunday–Saturday calendar
rows**: the (possibly partial) week containing the 1st is week 1, and each Sunday starts the
next. A month spans 4–6 weeks. Example: 1 Nov 2025 was a Saturday, so it alone is week 1 and
Sun 2 – Sat 8 Nov is week 2. Use today's date in **UTC** (CI and tags are UTC).

This is a project convention, not standard CalVer (which uses week-of-*year*); do not "correct" it.

```bash
first=$(date -u -d "$(date -u +%Y-%m-01)" +%w)       # weekday of the 1st, Sunday = 0
day=$(date -u +%-d)
W=$(( (day - 1 + first) / 7 + 1 ))
V="$(date -u +%y).$(date -u +%-m).$W"                # e.g. 26.11.3
git fetch --tags origin
git rev-parse -q --verify "refs/tags/v$V" && echo "v$V exists"
```

If `v$V` already exists (a second release, or a hotfix, in the same week), append a fourth
segment counting from 1: `26.11.3.1`, `26.11.3.2`, … Check each candidate against the tags.
Also check `gh release list` for a **draft** with that name; a stale draft is harmless (it
gets reused) but tell the user it is there.

The version records when the release was *cut* (the bump PR). If the release PR merges in a
later week, keep the version; do not re-bump.

## 2. Pre-flight

Run these and report the results before changing anything:

```bash
git fetch origin
git log --format='%h %s' origin/develop..origin/main       # what main has that develop lacks
git diff --stat $(git merge-base origin/main origin/develop) origin/main   # must be empty
git rev-list --count origin/main..origin/develop           # commits to ship
gh pr checks --watch=false $(gh pr list --base develop --state open --json number -q '.[].number') 2>/dev/null
gh run list --branch develop --workflow ci.yml --limit 1   # last develop CI must be green
```

- **`main` → `develop` content.** `main` normally *does* have commits that `develop` lacks: the
  merge commits of earlier release PRs, because `develop` never takes those in. That is fine,
  and it's why this compares content, not ancestry. If the `git diff --stat` above is **not**
  empty, a hotfix went to `main` without being merged forward. Stop and ask; it needs a
  `main` → `develop` PR first.
- **CI** runs on PRs only (`ci.yml` has no push trigger for `develop`), so the last
  `gh run list` entry may be old. What counts is that every PR being shipped passed CI, and
  branch protection already enforced that.
- **PRs being shipped:** list every PR merged into `develop` since the last tag. Use the last tag's
  date (`git log -1 --format=%cI <last-tag>`), not its author date:
  ```bash
  gh pr list --base develop --state merged --search "merged:>$LAST_TAG_DATE" \
    --json number,title,labels --limit 200
  ```
  Flag any PR with no label from `.github/release-drafter.yml`. Unlabelled PRs land in an
  uncategorised bucket, so ask the user to label them, or label them yourself if the category
  is obvious, before going on.
- **Release notes preview.** The GitHub release notes, which are also what the in-app What's New
  dialog shows, are generated by release-drafter only after the release PR merges, minutes
  before `release.yml` publishes them. So preview them now, while labels and titles can still
  change. Render the PR list exactly as `.github/release-drafter.yml` will. These rules were
  checked against the published v26.9.2 notes:
  - PRs with no category label come **first**, ungrouped, directly under "What's Changed"
  - then the `categories` in file order. A PR appears in **every** category its labels match,
    not only the first, so a PR labelled `enhancement,radio` is listed twice
  - newest merge first within each group, one line per PR, using `change-template`
    (`- $TITLE (#$NUMBER) @$AUTHOR`); empty categories are left out
  - PRs labelled `release` (the `exclude-labels`) are left out entirely

  Show the preview to the user. Fix anything that reads badly at its source: retitle the PR
  (`gh pr edit <N> --title`) or change its labels. Don't plan to hand-edit the notes after
  merge. The preview also seeds the release PR body and the ROADMAP entry.
- **Deferred or manual checks:** read project memory for gate checks marked deferred, such as
  nf0t-core A3's database migration and `log4om-migrate`. List them and ask whether this release
  ships with them still deferred.

## 3. Version-bump PR into `develop`

Branch: `chore/release-$V`. Change:

| File | Change |
|---|---|
| `CMakeLists.txt` | `project(NF0T-Logger VERSION $V ...)`. This is what `release.yml` reads. |
| `README.md` | the "currently at **v…**" line |
| `ROADMAP.md` | a `## v$V — <headline> ✓ shipped` entry summarising the release in prose, using the preview from step 2 |

There is deliberately no `CHANGELOG.md`. The GitHub release notes are the changelog.

Commit as `chore: release v$V`. Open the PR with the **`release`** label (excluded from the
release notes) and squash-merge it when the user approves.

## 4. Release PR `develop` → `main`

```bash
gh pr create --base main --head develop \
  --title "v$V — <headline>" --body-file <release-notes preview + verification/deferred notes> \
  --label release
```

The `release` label matters: without it, this PR is listed at the top of its own release notes.

- Title: `vX.Y.Z — <headline>` (not conventional-commit style). The user picks the headline.
- `develop`'s branch protection means CI must pass on the PR. `develop` is not deleted on merge,
  because protected branches are exempt from auto-delete.
- On approval: `gh pr merge <N> --merge --match-head-commit <sha>`.

## 5. Watch the automated release

The push to `main` starts two workflows:

- `release-drafter.yml` updates the draft notes.
- `release.yml`: `detect-version` → Windows NSIS + Linux AppImage → GPG sign → attach to the
  draft → publish (last step).

```bash
gh run list --branch main --workflow release.yml --limit 1
gh run watch <id> --exit-status
gh release view "v$V" --json isDraft,isImmutable,assets \
  --jq '{isDraft,isImmutable,assets:[.assets[].name]}'
```

Done when `isDraft: false` and exactly four assets are attached: the `.exe`, the `.AppImage`,
and a `.asc` for each.

**If a job fails before publishing:** the release is still a draft. Fix forward on `develop`,
then `gh run rerun <id> --failed`, or re-run `release.yml` with `workflow_dispatch`. Do **not**
publish to "unstick" it.
**If the draft notes need correcting**, edit them while still a draft:
`gh release edit "v$V" --notes-file <file>`. This edits the notes only and does not publish.
**If `sign-and-upload` reports the release is already published:** stop and tell the user. That
tag is burned; the fix is a new version with a fourth segment, never reusing the name.

## 6. After

- `git checkout develop && git pull --ff-only origin develop`, and delete the local
  `chore/release-*` branch.
- The in-app What's New dialog fetches the GitHub release notes for the running version, so
  check that the published notes read well.
- Update project memory: the shipped version, and any deferred checks that were accepted or
  cleared.
